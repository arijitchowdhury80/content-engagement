# WU-24 — Deploy to a shareable URL

Reasoning: `docs/05-execution-plan.md` § WU-24 · Asana `1217199734270443`
No source task — implied by acceptance criterion 6 (shareable without Arijit present)
Tier: inline · **Blocked by: VPS SSH access — needs Arijit**

## The criterion this unit exists to satisfy

**A localhost server or an artifact link fails criterion 6.** The test is: someone else,
on their own machine, unauthenticated, opens a real domain in a browser and it works.
Anything that requires Arijit to be present, screen-sharing, or running a dev server
does not count. The whole point is a URL he can send.

## The blocker

Target is the **Hermes VPS + Caddy**. Use the **`hostinger-vps-ssh`** skill — it holds the
connection procedure and the SSH_ASKPASS workaround needed in non-tty sessions. Credentials
live in the Hermes workspace `.env.local`.

A preflight check of VPS reachability was attempted 2026-08-05 and was **permission-denied**,
so access is unconfirmed. Confirm it before planning the deploy, and if it is unavailable
ask Arijit rather than improvising a different host.

There is prior art for exactly this deploy shape in memory: a reference note on the
**Caddy deploy path for the `bible` site on this VPS** records the real host filesystem
path for serving static files. Read it before inventing a path — the standing rule is to
enumerate what exists first.

## Inputs

- `docs/50-prototype/frame1/` (WU-21), `frame2/` (WU-22), `shared/`, `agent-layer/` (WU-23)
- Live Algolia index from WU-20
- **Search-only API key**, scoped to the demo index. This is a public page: an admin or
  write key in client JS on a public URL is a credential leak, not a demo detail.

## Method

1. Confirm VPS access via `hostinger-vps-ssh`. If unavailable, stop and ask.
2. Read the existing Caddy config and the bible-site deploy path before adding anything.
   Do not restructure someone else's working server config to fit this project.
3. Decide the URL shape. Both frames must be reachable, and a reviewer must be able to
   switch between them without instructions — a landing page with two clear entries, or
   an in-page toggle. Whichever WU-19 specified.
4. Build for production. Verify the search-only key is what ships, and that it is scoped.
5. Deploy static output. Caddy serves it over HTTPS on a real domain.
6. **Check the served surface, not the build output.** Load the real URL in a browser after
   the final change. This is the standing rule and it is the exact failure this project
   keeps guarding against: code fixed, live page stale.
7. Test unauthenticated, in a fresh profile or private window — a logged-in session on
   Arijit's machine proves nothing about criterion 6.
8. Test on a phone against the real URL, not a resized desktop window.

## Outputs

- Live HTTPS URL, unauthenticated, both frames reachable
- `docs/60-show/deploy-notes.md` — URL, host path, Caddy config diff, key scope, rollback
- `docs/60-show/screenshots/deployed-<frame>-<viewport>.png` — from the live URL

## Verify

```bash
URL="https://<the-real-url>"    # fill in
# served surface, unauthenticated, real domain
curl -sI "$URL" | head -3
curl -s "$URL" | grep -ciE "<title|algolia"
# the shipped page must NOT contain an admin/write key
set -a; . /Users/arijitchowdhury/Dropbox/AI-Development/RAG/Algolia-Central-Spectrum/.env.local; set +a
curl -s "$URL" | grep -q "$ALGOLIA_ADMIN_API_KEY" && echo "FAIL: ADMIN KEY EXPOSED" || echo "no admin key in served page: OK"
curl -s "$URL" | grep -q "$ALGOLIA_WRITE_API_KEY" && echo "FAIL: WRITE KEY EXPOSED" || echo "no write key: OK"
# both frames reachable
for f in frame1 frame2; do printf "%-8s %s\n" "$f" "$(curl -s -o /dev/null -w '%{http_code}' "$URL/$f")"; done
```

Then open it in a private window on a different device. If that fails, the unit is not done.
