API calls are like door swings at a very busy store: one customer entering is harmless, but autocomplete, filters, page loads, and eager bots can turn that door into a blur. The trick is not to stop the door from moving, but to make sure every swing is intentional. Short version: yes, every single request sent to an Algolia index counts as one billable search operation, regardless of whether the query is empty, a full string, or a set of filters. ### What counts as a request In Algolia, a "request" is any time your frontend or backend asks the engine for data. This includes: * **Keystrokes:** In a search-as-you-type implementation (like [InstantSearch](https://www.algolia.com/doc/guides/getting-started/quick-start/tutorials/account-metrics-with-the-dashboard/#usage-activity)), a new request is typically sent with every character the user types. * **Filters & Pagination:** Every time a user applies a facet filter or clicks to the next page of results (changing the `offset`), a new query is sent to retrieve the updated set of records. * **Page Loads:** If your site displays default results when a user lands on a category page, that is an "empty search" request and it is billable. * **Query Suggestions:** Requests to a [Query Suggestions index](https://support.algolia.com/hc/en-us/articles/10291951587473-Do-Query-Suggestions-increase-the-number-of-billable-requests) are billed as standard search requests. ### How this affects cost and rate limiting Because the volume of requests is driven by your frontend implementation, you have several levers to control costs: 1. **Frontend Optimization:** You can reduce requests by triggering a search only after a minimum number of characters are entered. While this saves money, be careful not to make the search feel "laggy" to the user. 2. **Request Bundling:** Use `multipleQueries` to retrieve both search hits and query suggestions in a single billable operation rather than two separate calls. 3. **API Key Rate Limiting:** To protect against bot spikes that can cause massive overage charges, you can create a dedicated [Search API Key with rate limits](https://support.algolia.com/hc/en-us/articles/15434270755985-Why-is-it-important-to-create-a-rate-limited-API-Key) (e.g., limiting queries per hour per IP). * *Recommendation:* Start with a high limit to avoid blocking real users and gradually tighten it based on your [API Monitoring logs](https://support.algolia.com/hc/en-us/articles/26829082868113-What-does-the-Count-metric-mean-in-the-Top-rate-limited-IPs-section). If you are using a backend search implementation, remember that Algolia sees all traffic coming from your server's single IP, so standard API key restrictions won't work—you'll need to handle rate limiting at your own server or WAF level. Migrating a search platform is like moving into a new house: you don't just dump everything from the old place into random boxes and hope for the best; you use the move as an excuse to declutter and organize your belongings so the new layout actually works. The short version is that migration to Algolia is a structured three-step process of data import, relevance tuning, and UI implementation. Because Algolia doesn't search your data sources directly, you aren't "switching" a connection so much as you are establishing a new, high-performance index of your data. Here is how the mechanism actually works: 1. **Data Import**: You push your records into Algolia using [API clients](https://academy.algolia.com/training/41a9c4a6-b158-11ee-8b2d-06ff0cab3fa7), JSON files, or direct database integrations. If you use a platform like Shopify or Magento, this is often handled via scripts within those integrations. 2. **Relevance Configuration**: Once your data is in, you fine-tune how Algolia understands it. This is where you move beyond basic keyword matching to use tools like [Dynamic Re-Ranking](https://www.algolia.com/customers/co-op), which allows you to see positive results in a matter of weeks via A/B testing without manually writing endless rules. 3. **UI/UX Implementation**: You connect your frontend to the Algolia engine using front-end API clients. This allows you to build a modern search experience without having to manage the underlying infrastructure. For teams with complex environments, the [Algolia CLI](https://www.algolia.com/developers/algolia-cli) is a critical tool for migrating records and configurations across different applications, providing a way to snapshot and revert indices if you need to iterate on your setup. **My recommendation**: Don't try to replicate your current platform's logic exactly. The biggest mistake in migration is "lifting and shifting" old search behaviors that weren't working. Instead, start with a clean data import and let Algolia's AI-driven relevance do the heavy lifting first, then layer in your specific business rules.
